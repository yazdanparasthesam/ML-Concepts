🧪 25. Error Analysis — از پایه تا Senior ML

حتماً. این بخش واقعاً یکی از تفاوت‌های اصلی Junior/Intermediate ML با Senior ML Engineer است.

یک Junior ممکن است بگوید:

F1 = 0.91

اما یک Senior می‌پرسد:

این 9٪ خطا دقیقاً کجا اتفاق می‌افتد، چرا اتفاق می‌افتد، چه کسانی/چه داده‌هایی را تحت تأثیر قرار می‌دهد، و برای کاهش آن چه تغییری بیشترین ROI را دارد؟

1. Error Analysis چیست؟

Error Analysis یعنی بررسی سیستماتیک predictionهای مدل برای پیدا کردن:

مدل کجا اشتباه می‌کند؟ چه نوع نمونه‌هایی برای مدل سخت هستند؟ آیا خطاها الگوی مشخصی دارند؟ آیا مشکل از model است یا data؟ آیا label اشتباه است؟ آیا feature کافی نداریم؟ آیا distribution تغییر کرده؟ آیا threshold اشتباه است؟ آیا یک گروه خاص performance ضعیف‌تری دارد؟

یعنی به جای اینکه فقط بگویی:

$$ F1=0.91 $$

می‌گویی:

$$ \boxed{ Where,\ Why,\ and\ How\ does\ the\ model\ fail? } $$

2. چرا Error Analysis از Hyperparameter Tuning مهم‌تر است؟

فرض کن:

Model A F1 = 0.91

و با tuning می‌توانی:

F1 = 0.913

اما Error Analysis نشان می‌دهد:

Product A F1 = 0.97 Product B F1 = 0.94 Product C F1 = 0.71

اگر Product C بخش مهمی از business باشد، احتمالاً:

رفع مشکل Product C ارزش بسیار بیشتری از tuning برای رسیدن از 0.91 به 0.913 دارد.

3. یک مدل ذهنی مهم

Performance کلی:

$$ Metric_{global} $$

در واقع aggregation تعداد زیادی sub-population است.

مثلاً:

$$ F1_{global} $$

می‌تواند ترکیبی از:

Customer type Product Region Time Transaction amount Device Language Age group

باشد.

پس:

$$ \boxed{ Global\ Metric\ can\ hide\ local\ failures. } $$

4. اولین مرحله: Confusion Matrix

در classification ابتدا:

Predicted Positive Predicted Negative
Actual Positive TP FN
Actual Negative FP TN

داریم.

5. False Positive

False Positive:

$$ Actual=0,\ Prediction=1 $$

یعنی:

مدل گفته positive، ولی واقعاً negative بوده.

مثلاً Fraud Detection:

Normal transaction ↓ Model → Fraud

ممکن است مشتری واقعی را block کنیم.

6. False Negative

False Negative:

$$ Actual=1,\ Prediction=0 $$

یعنی:

مدل positive واقعی را از دست داده.

مثلاً:

Fraud transaction ↓ Model → Normal

Fraud عبور می‌کند.

7. چرا باید FP و FN را جدا تحلیل کنیم؟

چون علتشان معمولاً متفاوت است.

FP ممکن است ناشی از:
• threshold پایین • feature ambiguity • false positive patterns • noisy data

باشد.

FN ممکن است ناشی از:
• signal ضعیف • rare patterns • threshold بالا • missing features

باشد.

8. فقط تعداد FP/FN کافی نیست

مثلاً:

FP = 1000 FN = 100

به‌تنهایی نمی‌گوید کدام مهم‌تر است.

باید cost را بدانیم.

مثلاً:

$$ Cost(FN)=100 $$

و:

$$ Cost(FP)=1 $$

در این صورت:

$$ 100 FN \times 100 = 10,000 $$

در حالی که:

$$ 1000 FP \times 1 = 1,000 $$

پس FN بسیار مهم‌تر است.

9. Cost-Based Error Analysis

در سطح Senior باید error را به business cost وصل کنی.

$$ Expected\ Cost = C_{FP}FP+C_{FN}FN $$

مثلاً در fraud:

$$ C_{FN} \gg C_{FP} $$

اما در بعضی سیستم‌ها برعکس است.

10. Error Analysis فقط برای Classification نیست

در regression هم می‌توانی بررسی کنی:

$$ e_i = y_i - \hat{y}_i $$

و بپرسی:

کجا error بزرگ است؟ چه گروهی error بیشتری دارد؟ آیا error با target magnitude افزایش می‌یابد؟ آیا residual pattern داریم؟

11. Residual Analysis

برای regression:

$$ Residual = y - \hat{y} $$

اگر residualها pattern داشته باشند، احتمالاً مدل چیزی را یاد نگرفته.

مثلاً:

Actual ^ | • | • | • | • +----------------> Prediction

اگر residualها random باشند، وضعیت بهتر است.

12. Error Distribution

Residual distribution را بررسی کن.

مثلاً:

Residual ^ | /\ | / \ |_____/____\____ 0

اگر:

$$ E[e] \neq 0 $$

باشد، ممکن است bias سیستماتیک داشته باشیم.

13. Error Analysis باید از Dataset شروع شود

یک dataframe برای prediction بساز:

df["prediction"] = model.predict(X) df["probability"] = model.predict_proba(X)[:, 1] df["error_type"] = ...

مثلاً:

id true_label prediction probability error_type customer_group product region timestamp

این تبدیل prediction به analysis dataset بسیار مهم است.

14. Error Taxonomy

یک Senior معمولاً errorها را دسته‌بندی می‌کند.

مثلاً در fraud:

Errors │ ├── False Positive │ ├── False Negative │ ├── Rare Pattern │ ├── Missing Feature │ ├── Label Noise │ ├── Data Quality │ ├── Distribution Shift │ └── Model Limitation

15. Error Bucketing

به جای بررسی تک‌تک predictionها، آنها را bucket می‌کنیم.

مثلاً amount:

0–100 100–500 500–1000 1000–5000 5000+

بعد metric را برای هر bucket محاسبه می‌کنیم.

16. Error Analysis بر اساس User Group

مثلاً:

User Type Recall ----------------------- New Users 0.62 Existing Users 0.94

مدل global:

Recall = 0.91

به نظر خوب است.

اما:

New Users مشکل جدی دارند.

17. Specific Products

مثلاً payment model:

Product A → F1 = .95 Product B → F1 = .93 Product C → F1 = .67

ممکن است Product C:

• رفتار متفاوتی داشته باشد • featureهای متفاوتی داشته باشد • label quality پایین‌تری داشته باشد • data کمتری داشته باشد

18. Time-Based Error Analysis

performance را بر اساس زمان بررسی کن:

Jan → F1 .93 Feb → F1 .92 Mar → F1 .91 Apr → F1 .75

این یک red flag است.

ممکن است:

$$ Concept\ Drift $$

یا:

$$ Data\ Drift $$

رخ داده باشد.

19. Seasonal Error

گاهی مدل در:

Weekdays

خوب است ولی:

Weekends

بد.

یا:

Normal days → .95 Holiday → .72

این ممکن است نشان دهد مدل seasonality را درست capture نکرده.

20. Error Analysis و Distribution Shift

اگر:

$$ P_{train}(X) \neq P_{production}(X) $$

باشد، performance ممکن است کاهش پیدا کند.

مثلاً:

Training: Mobile = 30% Production: Mobile = 80%

ممکن است model behavior تغییر کند.

21. Feature-Level Error Analysis

فرض کن FNها را جدا می‌کنی.

می‌بینی:

FN: Average transaction amount = low Device age = new Velocity = high

شاید:

مدل در ترکیب این featureها مشکل دارد.

اینجاست که Feature Engineering می‌تواند ارزشمند شود.

22. Error Analysis برای Interactionها

فرض کن:

age income

هر دو به تنهایی خوب هستند.

اما:

$$ Age \times Income $$

ممکن است signal مهمی باشد.

مثلاً مدل برای:

young + high-income + high-velocity

زیاد اشتباه می‌کند.

این یک clue برای interaction feature است.

23. Rare Cases

یکی از مهم‌ترین بخش‌ها:

Rare cases

مثلاً:

Normal: 99.9% Fraud: 0.1%

ممکن است مدل روی majority عالی باشد ولی روی rare patterns ضعیف.

24. چرا Rare Cases مهم‌اند؟

چون metric global ممکن است آنها را پنهان کند.

مثلاً:

Accuracy = 99.9%

اما مدل:

Recall(Fraud) = 10%

دارد.

پس:

$$ Global\ Metric \neq Business\ Quality $$

25. Error Analysis و Class Imbalance

در class imbalance باید حتماً error را بر اساس class بررسی کنی.

مثلاً:

Normal: Precision = .99 Fraud: Recall = .52

Accuracy شاید 99% باشد.

ولی مدل برای هدف اصلی business ضعیف است.

26. Confidence-Based Error Analysis

Prediction probability را هم بررسی کن.

مثلاً:

True = 1 Pred = 0 Probability = 0.51

در مقابل:

True = 1 Pred = 0 Probability = 0.01

این دو FN کاملاً متفاوت‌اند.

27. Hard Errors vs Borderline Errors

Borderline Error

مثلاً:

$$ P(y=1|x)=0.48 $$

مدل uncertainty زیادی دارد.

Hard Error

مثلاً:

$$ P(y=1|x)=0.001 $$

ولی label واقعاً positive است.

Hard errors بسیار جالب‌اند.

ممکن است:

label غلط باشد feature missing باشد distribution shift باشد rare pattern باشد

28. Error vs Confidence

یک تحلیل بسیار مفید:

Probability Bucket Error Rate 0.0–0.1 2% 0.1–0.2 5% ... 0.9–1.0 15%

اگر high-confidence errors زیاد باشند:

مدل calibration یا data problem جدی دارد.

29. Calibration و Error Analysis

مثلاً مدل می‌گوید:

P(Fraud)=0.95

ولی در مواردی که probability حدود 0.95 است فقط:

70%

واقعاً fraud هستند.

مدل overconfident است.

این برای تصمیم‌های risk-sensitive مهم است.

30. Error Analysis و Threshold

فرض کن:

$$ threshold = 0.5 $$

است.

اما error analysis نشان می‌دهد:

0.4–0.6

بیشتر errors هستند.

می‌توانی threshold را تغییر دهی.

مثلاً:

$$ threshold = 0.35 $$

ممکن است Recall افزایش دهد.

31. Threshold Tuning خودش Model Improvement نیست

این نکته مهم است.

اگر:

$$ P(y|x) $$

مدل ثابت باشد و فقط threshold را تغییر دهی:

representation مدل تغییر نکرده.

فقط decision policy تغییر کرده.

پس:

Model Quality

و:

Decision Policy

را جدا کن.

32. Label Error Analysis

یکی از مهم‌ترین یافته‌ها:

بعضی model errors واقعاً model errors نیستند.

ممکن است:

$$ y_{observed} \neq y_{true} $$

باشد.

مثلاً:

Model prediction = Fraud Stored label = Normal

بعد investigation نشان می‌دهد:

label اشتباه بوده.

33. Noisy Labels

اگر label noise داشته باشی:

True → Fraud Annotation → Normal

مدل را نمی‌توانی به‌سادگی با tuning اصلاح کنی.

راه‌حل‌ها:

relabeling multiple annotators label auditing consensus labels probabilistic labels

34. Data Quality Errors

ممکن است مشکل:

Age = -20 Amount = 999999999 Country = NULL Timestamp = wrong timezone

باشد.

مدل روی چنین داده‌ای ممکن است fail کند.

35. Missing Feature

ممکن است مدل prediction اشتباه کند چون feature کلیدی در inference وجود ندارد.

مثلاً:

Feature: device_risk_score

در training موجود بوده ولی در production:

missing

این یک pipeline problem است، نه صرفاً model problem.

36. Training-Serving Skew

یکی از مشکلات بسیار مهم production ML:

$$ P_{training}(X) \neq P_{serving}(X) $$

مثلاً preprocessing در training:

log(amount)

ولی production:

raw(amount)

است.

مدل ممکن است ناگهان خراب شود.

37. Data Leakage و Error Analysis

گاهی metric بسیار خوب است ولی error analysis نشان می‌دهد:

بعضی featureها در production وجود ندارند.

مثلاً:

chargeback_status

که بعد از وقوع fraud مشخص می‌شود.

اگر آن را در training استفاده کرده باشی:

leakage.

38. Slice-Based Evaluation

این یکی از مهم‌ترین مفاهیم Senior ML است.

به جای:

$$ Metric(D) $$

محاسبه کن:

$$ Metric(D_s) $$

برای sliceهای مختلف.

مثلاً:

$$ F1_{country=IR} $$
$$ F1_{country=TR} $$
$$ F1_{country=DE} $$

39. Sliceها می‌توانند چندبعدی باشند

مثلاً:

Country = TR AND Device = Mobile AND User = New

ممکن است:

F1 = .55

باشد.

در حالی که global:

F1 = .91

است.

این یک hidden failure mode است.

40. اما مراقب Multiple Comparisons باش

اگر 10,000 slice بسازی:

Country × Product × Device × Age × Time × ...

احتمالاً بعضی sliceها به‌صورت تصادفی performance بد نشان می‌دهند.

بنابراین:

هر subgroup anomaly الزاماً واقعی نیست.

باید:

sample size confidence interval statistical significance effect size

را بررسی کنی.

41. Small Slice Problem

مثلاً:

Group A: N = 1,000,000 F1 = .91 Group B: N = 10 F1 = .60

نباید نتیجه بگیری:

مدل روی Group B افتضاح است.

چون:

$$ N=10 $$

خیلی کوچک است.

42. Confidence Interval برای Slice Metrics

مثلاً:

Group A: Recall = 0.91 ± 0.01 Group B: Recall = 0.82 ± 0.20

Group B uncertainty زیادی دارد.

پس قبل از تصمیم‌گیری:

data بیشتری لازم است.

43. Error Analysis و Fairness

Slice analysis می‌تواند fairness problems را هم آشکار کند.

مثلاً:

Group A: FNR = 5% Group B: FNR = 20%

این اختلاف ممکن است از:

data imbalance label quality feature quality representation threshold distribution

ناشی شود.

44. Error Analysis و Root Cause Analysis

هدف نهایی:

Error ↓ Pattern ↓ Hypothesis ↓ Root Cause ↓ Intervention ↓ Experiment

مثلاً:

FN زیاد ↓ Mostly new customers ↓ New customers feature history ندارند ↓ Model relies on historical behavior ↓ Cold-start problem ↓ Add onboarding/device/network signals

این دقیقاً workflow یک Senior است.

45. Error Analysis نباید فقط Descriptive باشد

گفتن:

70% errors مربوط به Product C است.

کافی نیست.

باید بپرسی:

چرا؟

و سپس:

Product C ↓ Different user behavior ↓ Training data insufficient ↓ Model under-represents this population

46. Error Analysis و Hypothesis Testing

فرض کن می‌گویی:

مدل روی mobile بدتر است.

این را باید تست کنی.

مثلاً:

$$ H_0: Performance_{mobile} = Performance_{desktop} $$

و:

$$ H_1: Performance_{mobile} \neq Performance_{desktop} $$

اما فقط p-value کافی نیست.

Effect size و CI هم مهم‌اند.

47. Error Analysis و Data Collection

گاهی نتیجه:

Model problem نیست؛ data coverage مشکل دارد.

مثلاً:

Training: Product A → 80% Product B → 15% Product C → 5% اما production: Product C → 40%

راه‌حل ممکن است:

جمع‌آوری data بیشتر برای Product C

باشد.

48. Error Analysis و Active Learning

می‌توانی سخت‌ترین نمونه‌ها را برای labeling انتخاب کنی.

مثلاً:

High uncertainty ↓ Select samples ↓ Human labeling ↓ Add to training

این:

$$ Active\ Learning $$

است.

49. Error Analysis و Hard Negative Mining

در classification مخصوصاً retrieval/search بسیار مهم است.

مثلاً:

Query: "apple" Wrong negative: "banana" Hard negative: "apple watch"

Hard negative بسیار شبیه positive است.

با اضافه کردن hard negatives می‌توان representation را بهتر کرد.

50. Error Analysis در Search/RAG

فرض کن RAG داری.

به جای فقط:

Answer Accuracy = 85%

باید بررسی کنی:

Retrieval Error Generation Error

51. Retrieval Error

اگر document درست اصلاً retrieve نشده:

User Query ↓ Retriever ↓ ❌ Correct document not retrieved

LLM نمی‌تواند answer درست بدهد.

پس:

مشکل generation نیست.

52. Generation Error

اگر document درست retrieve شده:

Query ↓ Correct Context ↓ LLM ↓ ❌ Wrong answer

اینجا مشکل generation/reasoning/prompt/model است.

این distinction در سیستم‌های Agentic/RAG بسیار مهم است.

53. Error Analysis در Computer Vision

مثلاً classifier:

Cat / Dog

errors را بررسی کن.

ممکن است:

Low light Occlusion Blur Small objects Multiple objects Unusual viewpoint

باشند.

بعد augmentation هدفمند انجام می‌دهی.

54. Error Analysis در NLP

مثلاً sentiment classification.

ممکن است model روی:

Sarcasm Negation Long sentences Slang Code-switching Typos Rare words

ضعیف باشد.

به جای tuning کورکورانه:

dataset را برای همین cases تقویت می‌کنی.

55. Error Analysis در Time Series

بررسی کن:

Hour Day Week Month Season Holiday Promotion

مثلاً:

Normal → RMSE = 10 Holiday → RMSE = 80

این ممکن است signal مهمی باشد.

56. Error Analysis در Fraud Detection

یک framework بسیار خوب:

Fraud Errors │ ┌──────────────┴──────────────┐ │ │ FP FN │ │ ┌─────┴─────┐ ┌──────┴─────┐ │ │ │ │ New User High Amount New Pattern Low Amount │ │ │ │ ▼ ▼ ▼ ▼ Feature Threshold Missing Weak Problem Issue Signal Signal

57. Error Severity

همه errors یکسان نیستند.

می‌توانی error را rank کنی:

$$ Severity_i = Probability_i \times Cost_i $$

یا مثلاً:

Critical High Medium Low

58. Error Prioritization

اگر 100 نوع error داری، همه را همزمان fix نکن.

اول:

$$ Expected\ Impact $$

را محاسبه کن.

مثلاً:

Error Frequency Cost Priority FP-New User 20% Low Medium FN-Fraud 5% Very High Critical Product C 10% High High

59. Error Analysis و Pareto Principle

ممکن است:

$$ 20\% $$

از error categories مسئول:

$$ 80\% $$

از business impact باشند.

پس اول همان‌ها را fix کن.

این بسیار بهتر از random tuning است.

60. Error Analysis و Model Iteration

چرخه حرفه‌ای:

Train ↓ Evaluate ↓ Error Analysis ↓ Find Failure Modes ↓ Hypothesis ↓ Data / Features / Model change ↓ Retrain ↓ Evaluate ↓ Error Analysis again

ML یک چرخه است، نه:

Train once → F1 → Done

61. Error Analysis و Experiment Design

هر تغییر باید hypothesis داشته باشد.

بد:

Let's try XGBoost.

خوب:

FN rate for new users is high because historical-behavior features are missing. Adding device and velocity features should reduce FN rate for this slice.

بعد experiment:

Baseline vs New Features

و فقط global metric را مقایسه نکن.

62. Global + Slice Metrics

مثلاً:

Metric Baseline New Model Global F1 .91 .92 New User F1 .65 .78 Existing User F1 .95 .94 Product C F1 .70 .82

حالا می‌فهمی واقعاً چه اتفاقی افتاده.

63. یک نکته بسیار مهم: Regression Error Analysis

برای regression فقط:

$$ RMSE $$

نگاه نکن.

Residual را بر اساس:

Target magnitude Customer Product Region Time Prediction range

بررسی کن.

64. Heteroscedasticity

ممکن است error با magnitude افزایش یابد.

مثلاً:

Small values: Error ≈ 2 Large values: Error ≈ 100

یعنی variance residual constant نیست.

ممکن است نیاز باشد:

log transform weighted loss different model quantile regression

را بررسی کنی.

65. Error Analysis و Calibration

در classification:

دو مدل ممکن است:

$$ F1 = .91 $$

داشته باشند.

ولی:

Model A: well calibrated Model B: overconfident

باشد.

اگر downstream decision بر اساس probability باشد:

Model A ممکن است بسیار بهتر باشد.

66. Error Analysis و Ranking

در ranking/search:

فقط accuracy کافی نیست.

بررسی کن:

relevant document missing؟ false positives در top-k؟ query categories؟ long-tail queries؟ ambiguous queries؟ zero-result queries؟

مثلاً:

Head queries → NDCG .95 Tail queries → NDCG .61

این یک failure mode است.

67. Error Analysis در LLM

برای LLM حتی پیچیده‌تر است.

Error taxonomy می‌تواند:

Hallucination Retrieval Failure Reasoning Error Instruction Following Formatting Error Tool Selection Error Tool Execution Error Context Overflow Prompt Injection Safety Failure

باشد.

یعنی:

یک metric مثل accuracy برای LLM کافی نیست.

68. Error Analysis در Agentic AI

مثلاً agent داری:

User ↓ Planner ↓ Retriever ↓ Tool ↓ LLM ↓ Answer

اگر answer غلط است، باید مشخص کنی:

Planner error? Retrieval error? Tool error? Tool result interpretation? LLM reasoning? Final response?

این همان:

$$ Component-level\ Error\ Analysis $$

است.

69. Error Analysis و Observability

در production باید predictionها قابل trace باشند.

مثلاً ذخیره:

request_id model_version feature_version prediction probability threshold true_label timestamp error_type

تا بتوانی بعداً error را تحلیل کنی.

70. Model Version مهم است

مثلاً:

Model v1: FN = 10% Model v2: FN = 6%

ولی شاید:

Product C: v1 = 8% v2 = 20%

باشد.

پس deployment می‌تواند:

global metric را بهتر ولی یک critical slice را بدتر کرده باشد.

71. Error Analysis و A/B Testing

اگر مدل جدید deploy شد:

Control → Model A Treatment → Model B

فقط average metric را نگاه نکن.

Slice-level experiment هم انجام بده.

72. Error Analysis و Monitoring

بعد از deployment:

Offline Error Analysis ↓ Production Monitoring ↓ New Errors ↓ Error Analysis ↓ Retraining

یعنی Error Analysis بخشی از MLOps lifecycle است.

73. Error Analysis و Drift Detection

مثلاً:

Offline: Recall = 94% Production: Recall = 80%

باید بررسی کنی:

Data Drift? Concept Drift? Label Delay? Pipeline Issue? Feature Missing?

74. Label Delay

در production ممکن است ground truth فوری نداشته باشی.

مثلاً fraud واقعی:

30 روز بعد مشخص می‌شود.

پس Error Analysis real-time ممکن نیست.

باید:

Prediction ↓ Wait for label ↓ Join with outcome ↓ Error Analysis

انجام دهی.

75. Delayed Feedback

این در:

fraud churn credit risk recommendation

خیلی مهم است.

مدل ممکن است امروز prediction بدهد ولی label هفته‌ها بعد بیاید.

76. Error Analysis و Feedback Loop

یک خطر:

Model ↓ Decision ↓ Human ↓ New Label ↓ Training ↓ Model

اگر model bias داشته باشد، labels آینده هم می‌توانند biased شوند.

مثلاً model فقط بعضی transactions را برای بررسی انتخاب کند.

در نتیجه:

training data آینده تحت تأثیر model قبلی قرار می‌گیرد.

77. Selection Bias در Error Analysis

اگر فقط نمونه‌هایی که model flag کرده بررسی شوند:

کل population را نمی‌بینی.

مثلاً fraud model فقط flagged transactions را می‌فرستد برای investigation.

پس درباره unflagged transactions uncertainty داری.

78. Error Analysis و Counterfactual Thinking

بپرس:

اگر این feature تغییر می‌کرد، prediction عوض می‌شد؟

مثلاً:

Prediction = Fraud

و با حذف یک feature:

Prediction = Normal

این می‌تواند clue باشد، ولی:

counterfactual ≠ causal explanation

79. Error Analysis و SHAP

می‌توانی برای errors:

False Positive

SHAP را بررسی کنی.

مثلاً:

FP: device_risk +2.1 velocity +1.8 amount +1.2 location +0.8

می‌بینی چرا مدل این نمونه را fraud تشخیص داده.

80. ولی SHAP علت واقعی نیست

SHAP نشان می‌دهد:

model prediction چگونه به featureها نسبت داده شده.

نمی‌گوید:

feature واقعاً causal reason است.

این distinction بسیار مهم است.

81. Error Analysis و Clustering

یکی از تکنیک‌های جالب:

Errorها را cluster کن.

مثلاً تمام FNها را embedding کن:

FN embeddings ↓ Clustering ↓ Cluster 1 → rare device pattern Cluster 2 → international transactions Cluster 3 → new users

این می‌تواند failure modeهای ناشناخته را پیدا کند.

82. Error Analysis و Embeddings

در NLP/CV می‌توان:

Embedding ↓ Nearest neighbors ↓ Misclassified examples

را بررسی کرد.

مثلاً ببینی یک error به کدام نمونه‌های training شبیه است.

83. Nearest Neighbor Error Analysis

برای یک false negative:

FN sample ↓ Find nearest training samples ↓ Mostly normal? Mostly fraud? Mixed?

اگر neighbors mostly fraud باشند ولی model negative داده:

احتمالاً representation/model problem داریم.

84. Error Analysis و Data Augmentation

اگر errors عمدتاً:

blurred images

هستند:

augmentation:

blur augmentation

ممکن است منطقی باشد.

اما اگر errors عمدتاً:

wrong labels

هستند:

augmentation راه‌حل نیست.

85. Feature Engineering و Error Analysis

اگر:

FN: high transaction velocity

ولی model velocity را ندارد:

Feature engineering منطقی است.

مثلاً:

$$ velocity = \frac{\#transactions}{time\ window} $$

86. Model Selection و Error Analysis

گاهی error analysis می‌گوید:

complex nonlinear interactions

زیاد هستند.

آن‌وقت:

Linear model

ممکن است محدود باشد.

در چنین حالتی مدل‌هایی مثل:

Gradient Boosting XGBoost LightGBM Neural Network

ممکن است بهتر باشند.

87. ولی Model Switching آخرین راه نیست

Senior نباید بلافاصله بگوید:

Let's use a bigger model

اول:

بعد:

model.

92. Senior ML Mental Model

Junior:
Model accuracy is 95%.
Intermediate:
Model has high recall and acceptable precision.
Senior:

The global metric is acceptable, but the model has a concentrated failure mode: 65% of false negatives come from new users with less than three historical interactions. Their recall is 61% versus 94% for established users. This suggests a cold-start/data-coverage issue rather than a generic model-capacity problem. Before changing the model, I would test whether adding behavioral/device features available at inference time improves this slice, while monitoring the global metric and business cost.

این دقیقاً سطح تفکر Senior است.

🎯 جمع‌بندی Senior-Level

اگر فقط 10 چیز از Error Analysis بخواهی به خاطر بسپاری:

1. Global metrics failure modes را پنهان می‌کنند.
2. همیشه FP و FN را جدا بررسی کن.
3. Errorها را بر اساس slice بررسی کن: user/product/time/region/device/...
4. Rare cases را جداگانه بررسی کن.
5. Confidence predictionها را بررسی کن.
6. قبل از تغییر model، data و label quality را بررسی کن.
7. Training-serving skew و distribution shift را جدی بگیر.
8. برای هر failure mode یک hypothesis درباره root cause بساز.
9. تغییرات را با slice metrics + global metrics + business cost ارزیابی کن.
10. هدف Error Analysis پیدا کردن اقدام بعدی با بیشترین impact است، نه صرفاً پیدا کردن نمونه‌های اشتباه.

و مهم‌تر از همه:

$$ \boxed{ \text{A Senior ML Engineer doesn't just measure model performance; they diagnose model behavior.} } $$

و دقیقاً به همین دلیل است که در پروژه‌های واقعی، Error Analysis خیلی وقت‌ها ارزش بیشتری از Hyperparameter Tuning دارد.
